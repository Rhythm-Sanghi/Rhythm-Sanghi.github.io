The question behind the interface

Searching a name gives me occurrences. It does not tell me whether one function calls another, which relationship was resolved, or what an edit might reach. Threadmark brings those questions into one view, then lets me open the source behind an answer.

The project includes the analysis engine, local persistence, CLI and desktop interface. The useful boundary is between understanding code and presenting it: the interface should ask for a neighbourhood, not become a second analysis engine.

Which code depends on this?

This hand-written sample explains directed relationships. It does not run Threadmark or analyse your files. 

function readConfig() { return { limit: 10 }; }
function loadItems() { return readConfig().limit; }
function renderList() { return loadItems(); }
function exportItems() { return loadItems(); }

readConfig

Direct dependencies: none in this sample.

Reverse reachability: loadItems, renderList, exportItems.

A path through a static graph is a reason to investigate. It does not prove that every caller will run.

Two boundaries worth keeping

One engine for two clients

Rust owns discovery, Tree-sitter adapters, resolution, graph queries and Git comparison. React owns interaction and layout. Both the desktop app and CLI call the same engine. This keeps a relationship's meaning consistent whichever way I inspect it.

The desktop requests up to 24 nodes in a neighbourhood. The engine marks limits explicitly, so a bounded view cannot silently imply that no other dependencies exist.

Identity is separate from location

Symbol IDs use repository, path, language, qualified name and kind. Line numbers are excluded. Adding blank lines should move the source span without making every symbol look newly added. Renaming a file still changes identity and currently appears as additions and removals.

Conditions matter

Windows 11 x64 · Intel Core i7-1365U · 16 GB RAM · Rust 1.98.1 release build. No concurrent build. OS filesystem caches were not flushed: “new index” means a new database and parse cache, not a physically cold disk.

Whole-graph resolution and snapshot persistence still run during a refresh. Reusing parses helps, but does not remove those costs. The first adjacency load and broad real-world graphs add work not captured by a small warm query.

Where the answers stop

Static evidence cannot resolve arbitrary runtime dispatch, reflection or computed imports. Reverse impact is graph reachability, not a prediction of execution or test coverage. Git renames are not yet tracked as continuous identities.

The next useful improvements are affected-subgraph resolution and more efficient persistence, followed by broader desktop and long-session measurements. Linux and macOS have not been validated.
